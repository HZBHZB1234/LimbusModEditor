这些时间来自本机测量，部分测试与其它验证同时运行，受磁盘缓存、CPU 和后台负载影响，不能作为严格隔离的性能基准。数据库体积和结果一致性不依赖计时。分配量是操作期间累计托管分配，不是进程峰值或常驻内存；未测量完整桌面 UI 的端到端延迟。Bank 使用合成文件，不能代表所有真实音频文件的加速比。

宽查询分两步验证：先把数千次分批复核改成顺序扫描，测得 12.82 秒、1,448.95 MiB 累计分配；随后复用资源包及容器字符串、共享路径只判一次，降至 5.96 秒、93.72 MiB。两次结果哈希相同。

## 修改内容

- 资源事实表继续使用 v2，派生检索层升级到 d3。显示路径和对象编号逐条索引，资源包哈希、容器名、源路径每包只索引一次。检索取两层候选并集，再复核完整字符串，保留跨路径分隔符、中文、短查询等语义。
- 检索层写入复用预编译语句，顺序读取对象编号，移除逐批构造完整 LogicalPath 的开销。旧层重建后，空闲页超过 16 MiB 且超过总页数 20% 时压缩数据库；普通查询不执行压缩。
- 添加资源包外层/内层键的联合索引。资源地址定位先筛资源包，避免查询计划扫描全部资产。
- 宽查询改用顺序读取，复用共享字符串，并缓存包内公共路径的匹配结果。
- Spine 缓存加入 64 MiB 骨架、纹理及图集等主要负载预算；超大结果可返回给调用方，但不长期缓存。LRU 使用链表节点，修复大小写不同的键命中后无法正确更新淘汰顺序的问题。预算不包含对象头及调用方仍持有的结果，也不是进程内存上限。
- Bank 音频读取复用已有的流式头部/SNDH 校验，使用同一个文件句柄只读取选定 FSB，避免整个 Bank 与切片同时占用内存。

首次打开旧库会重建派生层并按需压缩，可能有一次较长等待；无需重新解析全部游戏资源包。只读短字符串或命中大量记录的搜索仍可能耗时数秒。

## 本机证据与复现

原始输出均位于 `artifacts/performance-20260919/`（不提交 Git）：

`IndexOptimizationBenchmarkTests.Measure_real_derived_index_and_queries` 通过 `LME_DERIVED_BENCH_SOURCE` 指定真实数据库，通过 `LME_DERIVED_BENCH_OUTPUT` 指定新的输出目录；测试用 SQLite backup 创建副本，并在副本上重建索引。比较旧代码时使用保留在 `build-before/` 的测试程序集，新代码使用 `build-after/` 或当前构建。每次应使用全新输出目录，避免覆盖证据。

`Measure_wide_query_on_existing_index` 使用 `LME_WIDE_BENCH_INDEX` 和 `LME_WIDE_BENCH_OUTPUT`；`BankAudioServiceTests.Measure_large_bank_slice_allocations` 使用 `LME_AUDIO_BENCH_OUTPUT`。这些基准没有设置对应环境变量时直接返回，不在普通回归中重复重建百万行数据库。
